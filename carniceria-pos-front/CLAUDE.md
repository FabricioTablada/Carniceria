## Project

Frontend for a butcher shop (carnicería) POS/ERP system. React 19 + TypeScript + Vite, talking to a separate backend (`carniceria-pos-backend`, not in this repo) at `VITE_API_URL` (see `.env`, e.g. `http://localhost:3000/api/v1`).

## Commands

```
npm run dev       # start Vite dev server
npm run build      # tsc -b && vite build (type-check then build)
npm run lint       # eslint .
npm run preview    # preview production build
npm run serve       # serve dist/ on port 4173 via npx serve
```

There is no test runner configured in this project (no test script, no test files). Verification on every change is `tsc -b` + `eslint` (touched files) + `npm run build` — no substitute for these three.

To type-check without a full build: `tsc -b` (uses the composite `tsconfig.app.json` / `tsconfig.node.json` split referenced from `tsconfig.json`).

Documented, not-implemented tech debt: an invoice-preference field per customer (`AUTO`/`FACTURA`/`TIQUETE`) was evaluated and deliberately dropped in Bloque 8.2 for adding scope with no real need — today the voucher type depends solely on whether the sale has a `customerId`.

## Working methodology (read before starting any redesign work)

This user runs UI/UX redesign work as a sequence of tightly-scoped **"Bloques,"** each closed with an explicit **"APROBADO"** before the next begins.

- **Never exceed the stated scope of the current Bloque.** If a brief lists "IMPLEMENTAR ÚNICAMENTE X," treat everything else as out of scope even if it looks like an obvious improvement — mention it, don't build it, unless broader autonomy is explicitly granted.
- **Big/ambiguous asks get a pre-implementation report first; well-scoped asks (a numbered checklist) get direct implementation, then a report.** Don't ask for approval on things that were already explicitly authorized in the message; don't implement things that were clearly meant as "analyze and propose first."
- **Every additive change to a shared component must be verified not to regress its other consumers.** Before shipping an extension to `DataTable`, `FormSection`, `KpiCard`, `Badge`, `MediaCard`, `PillGroup`, `Popover`, etc., confirm existing consumers still render identically.
- **No hardcoded colors, fonts, or spacing — tokens only.** Never introduce a literal oklch/hex/rgba value or an arbitrary Tailwind color; always resolve new colors from existing `--color-*`/`--pos-*` tokens in `src/index.css`.
- **Validation bar on every Bloque, without being asked:** `tsc -b` clean, `eslint` with zero *new* warnings/errors beyond the known pre-existing baseline (currently 3 `react-hooks/exhaustive-deps` warnings in `SalesPOSPage.tsx` — don't fix those as a drive-by, don't let the count grow), then `npm run build` green.
- **During an ERP-wide redesign block, defer minor issues instead of fixing them inline.** Auto-refresh/cache gaps, tabs not highlighting, pagination quirks, microinteractions, small calc adjustments — log them, don't fix them mid-block, unless they are a critical failure that blocks using the feature. Log format: one line per issue, module + description, appended to the "Sprint de Pulido Integral" backlog (see below). Ask the user where this backlog currently lives if unsure — it has moved between a memory file and a doc file over time; check both `ROADMAP.md`'s Pulido Integral section and prior session memory before assuming it's empty.
- **Before "integrating X into Y," verify Y's current state actually exists** — never invent new business functionality to satisfy an integration ask. Grep/read first; if the target doesn't exist, stop and ask rather than building the missing piece as a side effect.

## Permanent rules (apply to every future implementation and every future review)

- **Do not propose full rewrites of already-approved components/modules.** Once a module/pattern has shipped and been approved, extend it additively; a technical or functional reason of real weight is required to revisit its design, not just taste.
- **Always reuse existing logic, hooks, and components before writing new ones.** Check `src/components/ui/`, `src/components/common/`, and the target module's own `components/`/`hooks/` first.
- **Keep changes localized.** Don't rewrite a whole component when a targeted edit suffices; don't remove a component unless it's genuinely dead; don't change a public prop contract unless required by the task.
- **Never modify the backend** (`carniceria-pos-backend`) unless the user explicitly approves it for that specific task. No new endpoints, no business-rule changes, no DTO shape changes, without an explicit ask.
- **Never run destructive git operations, and only commit/push when explicitly asked.**
- **Don't run a "QA integral"/full regression pass unless asked** — most redesign Bloques explicitly say not to; targeted verification (`tsc -b`/`eslint`/`build` + spot-checking the touched screen) is the default bar, not a full manual QA sweep.

### POS-specific decisions (do not re-litigate without a strong reason)

The POS (`features/sales/pages/SalesPOSPage.tsx` + `layouts/PosLayout.tsx`) deliberately does **not** share the Backoffice's visual language — it has its own identity as a "professional sales terminal," reached after several rejected iterations, and considered **closed/approved** as of the final productivity-focused polish block (2026-08-02):

- **Own token namespace:** `.pos-surface` class in `src/index.css` defines `--pos-bg`/`--pos-panel`/`--pos-panel-2`/`--pos-border`/`--pos-ink`/`--pos-ink-muted`, applied via the `pos-surface` className on `PosLayout.tsx`'s outer wrapper, consumed via Tailwind arbitrary values (`bg-[var(--pos-panel)]` etc.) everywhere in POS-only files. These are **completely separate** from `--pos-content`/`--pos-content-muted` (also in `index.css`), which **are shared** with `DashboardLayout.tsx`'s `<main>` — never redefine those, it would recolor the entire Backoffice. **Important:** dialogs rendered in a Portal (e.g. the "Movimiento de caja" dialog in `PosLayout.tsx`, built on the shared `components/ui/Dialog.tsx`) are appended outside the `.pos-surface` DOM subtree — `--pos-*` tokens do **not** resolve inside them; those dialogs use the generic Design System tokens instead (`bg-muted`, `border-brand`, etc.), same as the rest of the ERP.
- **Light, clean surface** (not dark) — reversed from an earlier dark "terminal" direction after explicit user rejection: "no combina con el resto del sistema... debe verse limpio y luminoso." Brand color (`--brand`) is reserved for buttons/active states/primary actions only, never as a surface background.
- **`PosSidebar.tsx`** — icon-only floating "dock," no branding/logo, no expand/collapse button; expands on hover (`onMouseEnter`/`onMouseLeave`), collapses on mouse-leave. Same actions as always ("Nueva venta", "Buscar producto", "Descuento rápido", "Promociones", "Devoluciones", "Movimiento de caja", "Cerrar caja", "Corte de caja", "Ventas del día", "Productos vendidos" — labels deliberately reworded for clarity in the final polish block, same handlers) — never invent new rail items. - **`PosHeader.tsx`** — two stacked rows: the search bar (large, prominent, bordered on focus) + a secondary "Header Operativo" status strip with Caja/Cajero/Cliente/Hora/Ítems/Total-en-vivo as individual pill chips (`StatusItem`). **Since Bloque 8.3**, "Cliente" is a real selector, not a static label: it reads `selectedCustomer?.label || 'Público general'` and its `StatusItem` is clickable (`onClick={onOpenCustomerPicker}`, `StatusItem` gained an optional `onClick` prop for this — renders a `<button>` instead of a `<span>`), opening `CustomerSearchDialog.tsx` (see the "Módulo de Clientes" paragraph above) to search/select a customer or revert to "Público General" (always the first, fixed option in the dialog). Cards (`MediaCard.tsx`) intentionally de-emphasize the product image (`aspect-[2/1]`, not `aspect-[4/3]`) in favor of name/price/stock/action-button. Cards support optional corner badges (promotion/top-seller/low-stock, mutually exclusive, one per card) and a favorite star toggle.

### Feature-module structure

The app is organized as domain modules under `src/features/<module>/`: `audit`, `auth`, `batches`, `cashRegisters`, `cashSession`, `categories`, `customers` (Bloques 8.1–8.5), `documents`, `inventory`, `notifications`, `permissions`, `products`, `promotions`, `purchases`, `reports`, `returns`, `roles`, `sales`, `settings`, `suppliers`, `taxes`, `users`. Each module has its own subset of:

```
api/<module>.api.ts        # object exporting one method per operation, e.g. productsApi.getProducts
components/                # tables, forms, filters, badges — module-local, not shared
hooks/                     # one hook per operation: use<Resource>, use<Resource>s, useCreate<Resource>, useUpdate<Resource>, useUpdate<Resource>Status
pages/                     # <Resource>sPage, Create<Resource>Page, Edit<Resource>Page
schemas/                   # Zod schemas (note: cashSession uniquely uses `schema/`, singular)
types/                     # <module>.types.ts
```

Data flow is strict and has no exceptions in the audited code: **Page → hook (TanStack Query) → `api/<module>.api.ts` → `httpClient` (Axios) → backend.** No page or component calls `axios`/`httpClient` directly.

### Routing

`src/routes/index.tsx` declares all routes manually and flatly (no route-config array, no `createBrowserRouter`, no lazy loading). Every route repeats `<ProtectedRoute><DashboardLayout><Page /></DashboardLayout></ProtectedRoute>` explicitly — layouts are not applied via nested `<Outlet />`. The POS route uses `PosLayout` instead of `DashboardLayout`. Two guards:

- `ProtectedRoute` — requires `accessToken` in `authStore`, else redirects to `/login`.
- `RequireCashSession` — wraps only the POS route (`/sales/pos`); requires an open cash session (`cashSessionStore`), else redirects to `/cash-session/open`.

There is **no route-level permission guard** — `Can` (`components/common/Can.tsx`) only hides nav items/buttons; a real permission check for mutations happens only on the backend.

The sidebar nav is generated from the single source of truth `src/constants/navigation.ts` (`NAV_ITEMS`), each entry declaring `permission: Permission | null` and `enabled: boolean`.

### Auth & permissions

- `stores/authStore.ts` (Zustand, **no `persist` middleware**) holds `user`/`accessToken`/`isAuthenticated` — **no `refreshToken` field at all**. `accessToken` is memory-only (lost on every reload, by design — "A-01"); `user` is separately synced to `localStorage` (`authUser` key) so the UI has something to render before the silent refresh below resolves.
- **Real refresh-token flow exists** (this superseded an earlier no-refresh design — verify against `src/lib/htpp/` before assuming otherwise, this file is a snapshot). The refresh token itself **never reaches the frontend** — it travels exclusively as an `httpOnly` cookie set by the backend (`POST /auth/login`/`POST /auth/refresh`, `refreshTokenCookieOptions` in the backend's `config/env.ts`: `sameSite: 'none'`, `secure: true` unconditional since QA.APP.1 — needed for the cookie to survive Electron's cross-site `app://` → `http://127.0.0.1` origin, works on localhost too since that's a superset of what `SameSite=Lax` already allowed there). Pieces, all in `src/lib/htpp/`: `client.ts` (the single Axios instance, `withCredentials: true`, attaches `accessToken` from the store on each request) → on a `401` (except `/auth/login`/`/auth/refresh` themselves), calls `refreshManager.ts::refreshAccessToken()` (single in-flight promise — concurrent 401s all await the same real network call, required because the backend rotates+kills all refresh tokens on reuse of an already-rotated one) → retries the original request once with the new token; if the refresh itself fails, or the retry still 401s, calls `logoutManager.ts::performLogout()` (cancels + clears the TanStack Query cache, then `authStore.logout()` — shared by this automatic path and the manual "Cerrar sesión" button, so neither leaves stale cached data behind). `App.tsx` fires the same `refreshAccessToken()` once on mount (silent, swallows failure) to recover a session after a full page reload, using only the httpOnly cookie.
- `lib/htpp/client.ts` (note: folder is literally `htpp`, not `http`). `baseURL` resolves `window.__DESKTOP_API_BASE_URL__` first (set synchronously by `carniceria-pos-desktop`'s preload script when running inside Electron, since the real backend port is only known at runtime there) and falls back to the build-time `env.VITE_API_URL` otherwise — same frontend build serves both the web deployment and the Electron app.
- Permission codes live in `src/constants/permissions.ts` (`PERMISSIONS`) and **must exactly mirror the backend's seeded catalog** — do not invent new codes here. `usePermissions()` reads `user.permissions` from `authStore`.

### State management

Only two Zustand stores in the whole app, neither using `persist`: `stores/authStore.ts` (global) and `features/cashSession/store/cashSessionStore.ts` (the one module-local store). All other server state lives in TanStack Query's cache; local UI state (filters, dialog open/close) is `useState` per page.

### React Query conventions

Single `QueryClient` in `lib/query/queryClient.ts`: `staleTime: 5min`, `retry: 1` (queries) / `retry: 0` (mutations), `refetchOnWindowFocus: false`. Query keys follow `[resource, action, ...params]` (e.g. `['products', 'list', filters]`). Mutations invalidate by resource prefix (`queryClient.invalidateQueries({ queryKey: ['products'] })`), not by specific key.

## Metodología de trabajo que seguimos

Todo el trabajo se ejecuta como una secuencia de **"Bloques"** con alcance explícito, acotados y aprobados uno a la vez — nunca trabajo abierto/continuo sin un pedido concreto. Dos familias de Bloques, mismo espíritu, distinto propósito:

- **Bloques de rediseño UX/UI** (`Sprint UX/UI PIPASA V1` en adelante) — ver "Working methodology" arriba, sección específica de este archivo. Estándar visual de referencia: módulo Productos.
- **Bloques de QA** (`QA.1`–`QA.16B` para el ERP por módulos, `QA.APP.1`–`QA.APP.4` para Electron) — cada uno sigue el mismo patrón fijo: **análisis primero** (si el pedido es ambiguo o de alcance grande) → **aprobación explícita del usuario** → **implementación mínima del hallazgo real** → **validación** (`tsc`/`eslint`/`build`, y contra el sistema real corriendo cuando aplica) → **reporte en el formato pedido**. Un bloque de QA nunca reescribe algo que no rompió, nunca amplía alcance sin que el usuario lo pida, y nunca dos veces resuelve lo mismo de formas distintas.

## Cómo revisar un Bloque nuevo

1. Leer el pedido completo antes de tocar nada — identificar si es "bien acotado, implementar directo" (una lista numerada, un bug puntual) o "grande/ambiguo, reportar antes de implementar" (una auditoría, "revisá X", "quiero entender por qué pasa Y").
2. Si es un reporte de bug: **reproducir antes de asumir la causa** — leer el código real, no inferir desde el nombre de una función o un comentario viejo. Los comentarios y esta misma documentación son una fotografía, no la fuente de verdad — el código lo es.
3. Nunca dar un bloque por cerrado sin la validación que el propio bloque pide (`tsc -b`/`eslint`/`npm run build`, como mínimo; contra el sistema real corriendo cuando el hallazgo lo amerita, como se hizo en toda la serie QA.APP).

## Cómo implementar cambios

- **Reusar antes que crear.** Revisar `src/components/ui/`, `src/components/common/`, y `api/`/`hooks/`/`components/` del propio módulo antes de escribir código nuevo.
- **Cambio mínimo, localizado.** No reescribir un componente entero cuando alcanza un cambio puntual; no tocar un contrato público (`props`, forma de un DTO) salvo que el bloque lo exija explícitamente.
- **Nunca colores/fuentes/espaciados hardcodeados** — solo tokens (`--color-*`/`--pos-*` de `src/index.css`).
- **Todo cambio de extensión a un componente compartido** (`DataTable`, `FormSection`, `KpiCard`, `Badge`, etc.) se valida contra sus consumidores existentes antes de darlo por bueno — nunca asumir que no rompe nada.
- **Nunca modificar el backend** (`carniceria-pos-backend`) sin aprobación explícita para esa tarea puntual — mismo criterio para `carniceria-pos-desktop` cuando se está trabajando desde este repo, y viceversa.

## Cómo validar cambios

Mínimo no negociable en **todo** cambio, en cualquiera de los tres repositorios: `tsc -b` (o `tsc --noEmit` en el backend) limpio + `eslint` sin errores/warnings nuevos (el baseline conocido en este repo: 3 warnings `react-hooks/exhaustive-deps` en `SalesPOSPage.tsx`, no crecer ese número) + `npm run build` verde. Cuando el hallazgo lo amerita (bugs de integración, de Electron, de infraestructura de auth/sesión), validar además contra el sistema real corriendo — no alcanza con que compile: la serie QA.APP entera se apoyó en reproducir contra un `.exe` empaquetado real, nunca solo en revisión de código.

## Qué nunca debe hacerse

- **Refactors no pedidos.** Ver algo mejorable no es licencia para tocarlo — documentar como deuda técnica y seguir, salvo que el propio bloque autorice explícitamente esa mejora.
- **Cambios de arquitectura sin pedido explícito** — ni en el frontend, ni en el backend, ni en Electron. Las decisiones de arquitectura ya tomadas (ver "Decisions already made" arriba, y las secciones de `ROADMAP.md`) están cerradas; se necesita una razón técnica de peso real para reabrirlas, no solo preferencia.
- **Romper un módulo ya aprobado** — todo cambio a un componente/patrón compartido se valida contra sus consumidores existentes antes de darlo por bueno (ver arriba).
- **Ampliar el alcance de un bloque** más allá de lo pedido, aunque la mejora extra parezca obvia — mencionarla, no implementarla, salvo autorización explícita.
- **Llamadas de escritura contra servicios de terceros reales sin autorización explícita** (Alegra, R2/Cloudflare) — esto ya causó un incidente real durante QA.16A (factura duplicada real) y otro durante QA.APP.4 (downgrade real de una instalación) — ambos documentados como lección aprendida, no como algo que "ya no puede pasar" solo porque se escribió acá: seguir siendo explícito y cauteloso con cualquier llamada de escritura real.
- **Dar un bloque por cerrado sin la validación que el propio bloque pide.**

## Reglas para futuros QA

- Un QA nuevo **no repite** lo que QA.1–QA.16B/QA.APP.1–QA.APP.6 ya cerraron sin evidencia de una regresión real — partir de que esos hallazgos siguen corregidos, y solo re-verificar puntualmente si hay una razón concreta para sospechar lo contrario.
- **Reproducir antes de corregir**, siempre — nunca asumir la causa raíz de un síntoma sin leer el código real o reproducir contra el sistema corriendo.
- **Solo corregir el hallazgo real, con el cambio mínimo** — no aprovechar un bloque de QA para refactors, aunque se encuentre código mejorable en el camino (documentar como deuda técnica en `ROADMAP.md`, sección "DEUDA TÉCNICA Y DECISIONES PENDIENTES", en vez de tocarlo).
- **Todo hallazgo nuevo se documenta** en `ROADMAP.md` con la misma estructura ya establecida (bloque, hallazgo, severidad, corrección, cuándo implementarse) — no crear un documento nuevo para esto salvo que el propio bloque lo pida explícitamente.
- **Nunca ejecutar una llamada de escritura real contra un servicio externo** (Alegra, Cloudflare R2, o cualquier otro que se agregue en el futuro) como parte de una prueba, salvo autorización explícita y puntual para esa llamada específica.
